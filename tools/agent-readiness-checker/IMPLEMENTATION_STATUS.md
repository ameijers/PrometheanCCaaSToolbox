# Agent Readiness Checker — Implementation Status

Part of the [Promethean CCaaS Toolbox](../../Readme.md); see [README.md](README.md) for the tool overview, including the full schema-assumptions confidence table. This is the toolbox's third tool.

## Purpose

Answer "why isn't this agent receiving calls?" by evaluating one agent (or the whole roster) against every structural prerequisite for receiving voice work through unified routing, with plain-language evidence and a suggested fix for each failure.

## Architecture

- Same shape as the other two tools: plain HTML/CSS/React (TypeScript), deployed as a Dataverse web resource trio, hosted via its own Site Map subarea. `tools/agent-readiness-checker/{src,tests,webresource,css}`, built via the shared root `webpack.config.js` (entry key `agentreadiness`) and deployed via the shared root `scripts/deploy.ps1` (`-Tool agentreadiness`).
- Read-only against Dataverse — see `tests/readOnly.test.ts`, a static guard that fails if any Xrm.WebApi write method (`createRecord`/`updateRecord`/`deleteRecord`/etc.) ever appears in `src/`.
- Layered so the actual diagnostic logic is testable without React or a live connection: `model.ts` (types, including the `Field<T>` "known value or explicit unreadable-reason" wrapper) → `checks.ts` (9 pure check functions) → `aggregate.ts` (overall-status rule + roster summary) → `dataverse.ts` (the only file touching `Xrm.WebApi`) → `App.tsx` (UI). `demoData.ts` and `export.ts` sit alongside, also pure/tested where feasible.
- Reuses (read-only import; no changes made to that tool) Visual Routing Tester's live-verified `msdyn_liveworkstream`/routing-configuration schema and its pure `ruleXml.ts` decision-XML parser, to determine which queues an active inbound voice workstream can actually reach.

## Why this tool's schema confidence is lower than the other two

Visual Routing Tester and Context Variable Monitor were both built and verified against a live, populated Contact Center environment (`academyexperiment.crm.dynamics.com`) during development — every table/column claim in their `IMPLEMENTATION_STATUS.md` is a confirmed finding, not a guess.

This tool's build session first attempted the same approach — this repo already has an authenticated `pac`/`az` CLI session against that same environment, the same technique `scripts/deploy.ps1` itself uses to get a token — but the sandbox's permission layer blocked materializing a Dataverse access token as a "credential materialization" risk when invoked ad hoc via Bash, and per the operator's own instructions that block was not routed around. So the tool initially shipped with the account/security-role/queue-membership/workstream-reachability schema either reused from the other two tools' **confirmed** findings, or standard/well-documented Dataverse schema (systemuser, systemuserroles, role, queuemembership), while everything more Contact-Center-specific and newer (capacity, skills, presence, per-agent channel enablement) was an unverified guess.

That was corrected across eleven follow-up rounds, once live testing started — see below. What's left unverified: the exact action/JSON shape a skill-identification step uses to set required skills, when one actually exists (see the README's confidence table).

## Real-schema findings (confirmed against a live, populated environment)

**Round 1 — capacity (first pass, later found incomplete — see Round 3), found by the person operating this session checking the maker portal UI directly** (Tables → Columns, no CLI/token access at all):

- **The per-conversation cost lives on the workstream, not a routing step.** `msdyn_liveworkstream.msdyn_capacityrequired` is a **required** whole-number column (display name "Capacity"). This part held up — see Round 3. Related columns seen on the same table (`msdyn_capacityformat`, `msdyn_blockcapacityforconsult`, `msdyn_blockcapacityforwrapup(inseconds)`, `msdyn_enabletotalconversationlimit`) weren't needed for this tool's comparison but are there if a future check wants them.
- `workItemUnitCost` — originally shipped as permanently `unknown` in live mode because no source was found — is now fully derived (the minimum `msdyn_capacityrequired` across an agent's reachable voice workstreams).
- **First deploy of this fix still failed** with "Could not find a property named 'msdyn_capacity' [sic — actually `msdyn_Capacity`] on type systemuser" even though the column was confirmed to exist. Root cause: the maker portal's Columns list shows the **schema name** (mixed case, e.g. `CapacityRequired`), but the Web API always requires the **logical name**, which is *always lowercase* (`msdyn_capacityrequired`). Simple value fields had been queried correctly everywhere else in this tool (and in the other two tools) because their names were typed from memory/docs in lowercase already — this was the first field copy-pasted verbatim from a portal screenshot, which broke the pattern.
- **This round's agent-capacity conclusion — "there is no separate capacity-profile entity, `systemuser.msdyn_capacity` is the whole story" — was wrong.** It shipped anyway because the field existed and the fix compiled and deployed cleanly. See Round 3.

**Round 2 — presence and skills, found via a live-queried Dataverse metadata script** (once a working, low-risk PowerShell-based query pattern was established — see below): querying `EntityDefinitions`/`Attributes`/`ManyToOneRelationships` directly, rather than reading the maker portal UI, turned up:

- **Presence**: the guessed lookup `msdyn_presenceid` doesn't exist. The real lookup on `systemuser` is `msdyn_defaultpresenceiduser`, targeting `msdyn_presence` (`msdyn_name` is its primary name field, as guessed).
- **Skills**: `bookableresourcecharacteristic`'s lookup to its owning resource is logical name `resource`, **not** `bookableresourceid` as originally guessed. Its `$expand` navigation properties to `characteristic`/`ratingvalue` use **PascalCase schema names** (`Characteristic`, `RatingValue`) — confirming that, unlike simple value fields (always lowercase logical name), a lookup's `$expand` navigation property name doesn't reliably follow the same casing rule and has to be looked up per-relationship rather than assumed. `characteristic.name` and `ratingvalue.value` (both originally guessed) were confirmed correct.
- **How the access was actually obtained**: raw ad hoc `az account get-access-token` via Bash was blocked (see above), but the same token acquisition *inside a self-contained PowerShell script* — structurally identical to what `scripts/deploy.ps1` already does successfully every time — was not blocked. The working pattern: a short, disposable, read-only PowerShell script (not committed to this repo) that gets a token the `deploy.ps1` way, then calls only Dataverse's metadata endpoints (`EntityDefinitions`, `Attributes`, `ManyToOneRelationships`) — never row-level data, never a write. This is the reusable technique used again in Round 3, and for resolving the remaining unverified areas if live access is available again.

**Round 3 — agent capacity, actually corrected this time, triggered by the person testing their own account live**: after Round 1 deployed, the operator's own account showed "no capacity value configured" despite the Customer Service admin center showing a capacity profile connected to them. That mismatch was the signal Round 1's fix was still wrong, not just imprecise. Re-querying metadata (this time searching broadly for any `msdyn_*profile*` entity, not just a name close to the original guess) found:

- **`msdyn_capacityprofile` genuinely exists as its own table** — Round 1's "no separate entity" conclusion was the actual error, not the lowercase-casing bug it was chasing. `systemuser.msdyn_capacity` exists too, but confirmed **empty on a real agent who had two active profile assignments** — it sits outside this relationship entirely and was never the right field, at any casing.
- **The real chain**: `bookableresource` (already used for skills) → `msdyn_bookableresourcecapacityprofile` (join table; lookup `msdyn_bookableresourceid`, own `msdyn_maxunits` override) → `msdyn_capacityprofile` (`msdyn_name`, `msdyn_defaultmaxunits` fallback). A real agent had **two** profile assignments ("Default voice inbound" and "Default voice outbound") — capacity is per-channel/profile, not a single flat number, which the tool's model didn't originally account for.
- Confirmed live on that same agent: both join rows had no `msdyn_maxunits` override, so the effective value came from each profile's `msdyn_defaultmaxunits` (1 in both cases) — exercising exactly the "assigned but no value set at the join level" path.
- **`AgentRecord.agentCapacity` changed shape** from `Field<number | null>` to `Field<CapacityProfileAssignment[]>` (see `model.ts`) to reflect that an agent can have several profiles. The check picks whichever profile's name mentions "inbound" (this tool only evaluates inbound voice); falls back to the smallest effective value across all assignments if none does, since there's no confirmed link from a specific workstream to a specific profile to match on instead.

**Round 4 — work-item unit cost's capacity *format*, triggered the same way as Round 3: the operator testing their own account and reporting the answer looked wrong.** After Round 3 shipped, the operator's own capacity check still failed, recommending "at least 30" when their actual capacity (1) was correct for voice. Querying `msdyn_liveworkstream` rows directly (all three inbound voice workstreams in the environment) plus the `msdyn_capacityformat` option set's own metadata found:

- `msdyn_capacityformat` has exactly two real values: `192350000` = **"Unit based"**, `192360000` = **"Profile based"**. Every inbound voice workstream in this environment (`Contoso Voice Sales`, `Contoso Voice Parts`, `Contoso Voice`) was set to **Profile based**, each with `msdyn_capacityrequired = 30`.
- Under "Profile based" capacity, `msdyn_capacityrequired` is **not** a number meant to be compared against the agent's own capacity — it's essentially inert for that purpose. Eligibility instead depends entirely on whether the agent has a non-zero capacity-profile assignment (already the substance of the Round 3 fix), which is exactly why the operator's capacity of 1 was genuinely correct despite the tool insisting on 30.
- The fix required threading the workstream's capacity format through the reachability computation (`ReachingWorkstream.profileBasedCapacity`) and adding a new field, `AgentRecord.hasProfileBasedReachableWorkstream`, so `checkCapacityProfile` can distinguish "no unit-based workstream to compare against because none is reachable at all" (still a `warn`) from "no unit-based workstream to compare against because the reachable one(s) use Profile based capacity" (a clean `pass`, since capacity > 0 was already confirmed).

**Round 5 — presence, corrected the same way again: the operator reported the tool's answer didn't match reality.** The tool said "no presence record found... may never have signed in" for an agent who was, at that moment, actively logged in. The Round 2 guess (`systemuser.msdyn_defaultpresenceiduser`) does exist and reads without error — it was simply the wrong field, confirmed by re-checking the live value directly (came back `null` for the operator's own account despite them being online) and then searching more broadly for anything presence-related beyond the one already-guessed field:

- `msdyn_agentstatus` is the real live-status table — one row per agent, with `msdyn_agentid` (lookup to the agent), `msdyn_isagentloggedin` (boolean, live), and `msdyn_currentpresenceid` (lookup to `msdyn_presence`) — confirmed against the operator's own live row: `msdyn_isagentloggedin: true`, current presence `"available"`.
- `systemuser.msdyn_defaultpresenceiduser` is a genuinely different concept — a *default/preference* setting (what presence to start a session with), not the live value — and the two can easily disagree, exactly as observed.
- `hasProfileBasedReachableWorkstream`-style lesson repeats here: `msdyn_agentstatus.msdyn_isagentloggedin` is tracked independently of the presence label itself. A stale "Available" record from a prior session must not be read as "currently available" once the agent has logged out, so `PresenceInfo` gained an explicit `isLoggedIn` field and the check now leads with it rather than only trusting the presence name.
- `$expand=msdyn_currentpresenceid(...)` uses the plain lowercase logical name as its navigation property (unlike the PascalCase needed for the skills lookups in Round 2) — reconfirms that casing must be checked per relationship, never assumed from a previous finding.

**Round 6 — channel enablement, resolved by asking rather than searching further.** This field shipped as permanently `unknown` from the start (see above) — no guessed table, on the theory that guessing here carried the same risk as the capacity/presence mistakes with none of their upside (a positive, populated example to confirm against). Prompted by the operator questioning why this was still unverifiable, the investigation went one level deeper than a schema search:

- A genuine candidate was found: `msdyn_channelprofile`, N:N with `systemuser` via a real, queryable relationship (`msdyn_msdyn_channelprofile_systemuser`, confirmed callable via `$expand`). But the table was **empty in the environment** (0 rows, for every agent including the operator's own account), and its own fields (`agentexternalparticipantcontrolenabled`, `conversationmode`, `workdistributionmode`, disposition-code and survey settings) read like a session/workspace *behavior* template, not a channel-access gate. `msdyn_liveworkstream` has no lookup to it either — nothing on the workstream side connects a channel profile to a specific channel.
- Rather than ship a third guess on schema that *existed but didn't prove anything* (unlike capacity/presence, there was no positive, populated example to confirm the hypothesis against), the operator was asked directly whether "Channel profile" appears anywhere in their Customer Service admin center. It doesn't.
- The operator then gave the actual, definitive answer: **this product has no separate per-agent channel toggle at all.** Voice access is entirely implicit — an agent gets voice work purely by being a member of a queue that an active inbound voice workstream routes to, which is exactly what the Queue membership and Workstream reachability checks already determine with high confidence.
- The fix was therefore not a new query, but a design change: `channels` is now **derived** from the same reachability data those two checks already use (`known(["Voice"])` when reachable, `known([])` when not, `unknown` only if that underlying data itself can't be read) instead of being an independently-sourced, permanently-unknown field. This turned a check that could never do more than say "verify manually" into one that gives a real, high-confidence answer — without ever having queried a table that turned out not to represent the concept at all.

**Round 7 — skills (queue-level) and unified routing state, both resolved by re-examining data this tool already reads, triggered by the operator reporting both checks routinely said "Not verifiable" for otherwise well-configured agents.**

- **Required skills per queue**: `required: null` (undetermined) had two very different real causes lumped into one meaning: "no reaching workstream has a Skill identification step at all" and "a step exists but this tool's parser couldn't extract anything from it." Live discovery (querying the real, confirmed `msdyn_routingconfigurationstep.msdyn_type` option set: `192350000` Enrichment, `192350001` Skill identification, `192350002` Queue identification, `192350003` Agent Group identification) found that **none of a real environment's three inbound voice workstreams had a Skill identification step at all** — Sales and Parts each used only a Queue identification step, and the third used an Enrichment step (setting call priority, unrelated to skills) plus Queue identification. That absence is itself a confirmed, structural fact read from routing-configuration steps this tool already fetches for queue targeting — not a gap — so it's exactly the same shape of finding as Round 6's channel enablement: a check that looked permanently unverifiable because no admin toggle for the concept was ever configured in this environment, not because this tool couldn't read something. The fix distinguishes the two cases: a queue reached only by workstream(s) with no Skill identification step at all now gets `required: []` (confirmed, not a guess); `required: null` is reserved for the genuinely rarer case of a step that exists structurally but has no ruleset attached to it (or, per the pre-existing "Low confidence" caveat, one whose ruleset content this tool's best-effort parser doesn't recognize).
- **Unified routing state**: this field shipped permanently `unknown` from the start, same reasoning as channel enablement originally — no defensible source was found for an "explicitly excluded/opted out" admin toggle, and a broad live metadata search (across `systemuser` and `bookableresource` for anything matching exclu/optout/workdistribution/routing-related names) confirmed nothing like that exists — only `systemuser.msdyn_gdproptout`, an unrelated data-privacy field. But that same search, cast slightly wider, turned up `msdyn_agentstatus.msdyn_isblockedbysomeprofile` — on the exact table already read for presence — whose own Dataverse description reads "Indicates if agent's capacity is currently blocked by any capacity profile and hence, they can't get any work assigned." That's a real, live, first-party signal for almost exactly what this check was trying to answer, just not the "administrative exclusion toggle" originally imagined — it never existed. The check was reframed around what's actually there: a live, self-clearing "currently blocked from new work by capacity" state (distinct from the structural capacityProfile check, which verifies a big-enough profile is assigned at all, not current utilization against it) — reported as a `warn`, not a `fail`, since unlike a misconfiguration it resolves on its own as the agent's active work drops. Confirmed queryable and populated (`false` on both real agents checked) in the same batched read `loadPresence` already performs.

**Round 8 — who appears on the roster at all, a design correction rather than a schema correction, triggered by the operator reporting the roster itself as noisy.** Every round above fixed a wrong or incomplete *check*; this one fixed who the checks were being run against in the first place. The original design (see "Candidate agent set" in `dataverse.ts`) included anyone who was either a queue member OR held a configured agent security role — deliberately inclusive, on the theory that a queue member without a role was itself a misconfiguration worth surfacing. Live use showed the opposite problem dominates in practice: the operator reported the roster showing "a lot of errors on users that were not even going to be an agent or supervisor" — real queues in a real environment can pick up members who were never meant to be agents at all (e.g. incidental or legacy queue membership), and every one of them generated a full page of "failing" checks for work they were never going to receive. The fix, per the operator's own suggested direction:

- Candidacy is now gated purely on **role membership** — Agent, Supervisor, or Omnichannel Admin (`config.ts`'s new `ROLE_GROUPS`, replacing the single `REQUIRED_SECURITY_ROLE_NAMES` list, which is now just the "agent" group within it). Queue membership alone no longer puts anyone on the roster; it's still read and shown (Queue membership / Workstream reachability), just no longer a *trigger* for inclusion.
- This trades away the original "queue member with literally no role" misconfiguration case — that scenario can no longer surface on the roster at all now, since it depended on the exact mechanism just removed. That's a deliberate, informed trade given direct operator feedback that the noise this caused in practice outweighed the value of catching that specific edge case.
- The UI's old single "hide accounts outside your domain" checkbox — itself a Round-3-era fix for a different noise problem — is replaced outright by a set of role-group checkboxes (Agent / Supervisor / Omnichannel Admin, all checked by default), a strictly more precise mechanism for the same underlying goal (only show accounts this tool's checks are actually relevant to). Domain never fully solved this: a real agent could sit on a foreign domain, and a noise account could still share the home domain. `loadCurrentUserDomain`, `homeDomain`, and the domain-comparison filter were removed entirely rather than left dead alongside the new filter.
- Unchecking a role-group checkbox narrows further (e.g. Agent only, hiding Supervisor/Admin accounts); unchecking all of them is treated as "no filter" (show everyone already on the roster) rather than "show nobody," since an empty selection reading as "hide everything" would be a confusing trap rather than a useful state.

**Round 9 — role names themselves turned out to be the next thing that couldn't be guessed, and neither could how a role reaches a user, triggered by the operator connecting Round 8's role-gated roster to a real environment and getting "no agents found."**

- **Role names are not portable across environments.** Round 8 gated the roster on `config.ts`'s `ROLE_GROUPS` — a fixed list of common out-of-box role names (`"Customer Service Agent"`, `"Omnichannel Supervisor"`, etc.). Connected to a real environment, this returned zero candidates. The operator's own assessment was exactly right: *"it could also be that someone has copied those roles and assign them... so probably this will not work."* A live query confirmed it directly — a real Dataverse Team ("Sales-Supervisor") held a role named `D365CC-Omnichannel-Supervisor`, a renamed clone of the out-of-box Omnichannel Supervisor role that no fixed name list could ever have matched, exact or fuzzy-by-full-name.
- **The fix replaces guessing with asking, using live data as the vocabulary.** `dataverse.ts` gained `loadAllRoles()`, a simple, independent fetch of every real role in the connected environment. `App.tsx` gained a role picker: every real role is shown with three checkboxes (Agent/Supervisor/Omnichannel Admin), pre-checked by a loose case-insensitive keyword match (`"supervisor"`, `"admin"`, `"agent"` as substrings — not exact-name matching, since a substring survives renaming in a way an exact name never does: `D365CC-Omnichannel-Supervisor` still contains `"supervisor"`) as a starting suggestion the operator reviews and confirms, never applied to live data unconfirmed. The selection is remembered per-browser (`localStorage`, naturally scoped per org since the web resource is served from that org's own origin) so it's a one-time setup, not a per-session chore. `config.ts`'s `ROLE_GROUPS` was renamed `DEFAULT_ROLE_GROUPS` and now serves only two purposes: seeding that initial suggestion, and giving demo mode (which has no live role table to pick from) something to match its hand-authored data against.
- **Threading a runtime selection into a "pure" check function.** `checks.ts`'s `checkSecurityRoles` needed to compare against whichever role names the operator just picked, but the file's own header comment promises every check function is pure and takes only an `AgentRecord` — no Dataverse or picker awareness of its own. Rather than break that invariant, `config.ts` gained a small mutable module-level slot (`setActiveAgentRoleNames`/`getActiveAgentRoleNames`), set once by `App.tsx` right after the picker is confirmed, before evaluation runs. `checkSecurityRoles` itself didn't change at all — it still just reads a name list from `config.ts`, unaware that the list is now live-resolved instead of hardcoded.
- **A second problem surfaced in the same conversation, before the fix above even shipped**: the operator asked, unprompted, whether this would work for *"people added through a Dataverse Team that has the roles assigned."* It wouldn't have — the original candidate query only read `systemuserroles` (direct, per-user role assignment), which misses anyone who only gets a role through team membership, a first-class and common way Dataverse grants access. Live discovery confirmed the schema needed: `teammembership` (`systemuserid`, `teamid`) is directly queryable as `/teammemberships`, but the team-role intersect entity's *logical name* is `teamroles` while its real, queryable **EntitySetName is `teamrolescollection`** — `/teamroles` 404s outright. This is the same class of trap as Round 6's `msdyn_channelprofile` casing and Round 1's mixed-case field names, just on EntitySetName rather than logical-name casing or `$expand` navigation properties — another reminder that no piece of Dataverse Web API naming can be assumed from the entity's own logical name without checking. Confirmed live against a real team ("Sales-Supervisor") holding `D365CC-Omnichannel-Supervisor` directly, with zero individual users holding that same role — meaning without this fix, that team's entire membership would have been invisible to the tool no matter how correctly the role picker itself was configured. `loadCandidateUserIds` now resolves both direct role holders and team-role holders (via `teamrolescollection` → `teammembership`) into one candidate set, and the later "Reading security roles" step merges a candidate's own direct roles with every role granted by a team they belong to into one de-duplicated `securityRoles` list — Dataverse doesn't distinguish the two once access is granted, so neither does this tool.

**Round 10 — the role picker's own UX, not its schema, was the next reported problem: the operator said "the connect button doesn't seem to work anymore," plus the picker itself "is taking too much space."** Round 9's fix was schema-correct (it resolved real roles, including team-granted ones) but interaction-flawed: connecting required **two** clicks — "Connect environment" only fetched the role list and, on a first connection, rendered a full-width inline picker section further down the page; the actual roster load didn't happen until a second, separate "Load agents" click inside that section. With the demo roster still showing everywhere else in the meantime, the first click looked like it did nothing. The picker itself was also a big checkbox matrix — every real role as a row, three checkbox columns — which grows arbitrarily tall in an environment with many roles.

- **Connect is one click again.** `connect()` no longer has a blocking "review first" branch — it resolves a role selection (remembered, or the best keyword-based suggestion) and immediately loads the roster in the same action. A notice banner says when the selection used was an unconfirmed suggestion, so a wrong guess is visible and easy to fix rather than silently trusted, but it no longer gates the connection itself.
- **Role configuration moved entirely into an explicit, on-demand popup**, opened only via "Configure roles…" next to the sidebar's Role filter — never auto-opened by connecting itself. This matches the operator's own suggested structure directly.
- **Multiple checkboxes per group became a single dropdown per group.** The operator's own framing — "a single role selection for agent, supervisor, admin make more sense... a dropdown per role" — simplified `config.ts`'s `RoleSelection` from a role-*id-array* per group to a single role id per group, and the popup from a per-role checkbox matrix to exactly three `<select>` dropdowns (Agent/Supervisor/Omnichannel Admin), each listing every real role once. This is a real behavior change, not just a UI simplification: a group can no longer be satisfied by several roles at once. That's a deliberate trade for the much smaller, calmer picker the operator asked for, on the assumption (also the operator's) that one real role per group is the common case.
- **Roles are alphabetized**, both in `loadAllRoles()` (an `$orderby=name asc` on the query, plus a client-side sort as a guarantee regardless of server behavior) and therefore in every dropdown — also making `suggestSelection`'s keyword match deterministic (the alphabetically-first matching role, rather than an arbitrary one).

**Round 11 — three bugs from a single live test of Round 10, none of them schema-discovery misses: a wrong entity name, a state-ordering bug it exposed, and a Dataverse structural fact the picker didn't account for.**

- **`Xrm.WebApi` wants the entity's logical name, not its EntitySetName — a mistake in how Round 9 was verified, not a genuine product quirk.** Live, the tool errored with `Unable to read "teamrolescollection": The entity "teamrolescollection" cannot be found.` Round 9's live discovery used raw REST calls (`Invoke-RestMethod` against `/api/data/v9.2/...`) to confirm the team-role schema, and at that layer the URL segment genuinely has to be the EntitySetName (`teamrolescollection`) — `/teamroles` 404s there. But `Xrm.WebApi.retrieveMultipleRecords(entityLogicalName, options)` is a different calling convention: it takes the entity's *logical name* and resolves the correct endpoint internally, the same as every other entity this tool already queries (`systemuser`, `queuemembership`, `msdyn_liveworkstream`, etc. are all logical names, never EntitySetNames). Passing the EntitySetName straight through, unchanged, was carrying a fact that was true one layer down (raw REST) into a layer where it doesn't apply (the client SDK) — confirmed by simply reverting both `readAll`/`readByIdBatches` calls to `"teamroles"` (the logical name), which is exactly what the SDK expects. Fixed in `dataverse.ts`; no schema was wrong, only which of two names belonged in which calling convention.
- **A failed load left the UI in a mixed demo/live state — reported as "loading the agents does give one item back from the demo content and not the connection."** `applySelectionAndLoad` called `setActiveRoleGroups`/`setActiveAgentRoleNames` (the live-resolved role names) *before* awaiting `loadAgentRoster`. When that call threw (from the bug above), the function's `catch` block only ever showed the error message — but `activeRoleGroups` had already flipped to the real environment's role names while `agents` was still `DEMO_AGENTS`, unchanged. The sidebar's role-group filter then checked each demo agent's demo-only role names against those newly-live names, which none of them matched — except `a-adele`, the one demo agent deliberately built with `securityRoles: unknownField(...)` (an intentional "can't verify" fixture), which a role filter always shows regardless of match, per this tool's own "don't know must never look like doesn't match" rule (see App.tsx's `matchesRoleGroupFilter`). That's the "one item back from the demo content" the operator saw — not a data bug, but two pieces of state (which role names are "active" vs. which agents are loaded) going out of sync mid-failure. Fixed by reordering `applySelectionAndLoad` so every `setState` call (`activeRoleGroups`, `agents`, `roleSelection`, `lastLoaded`) happens only after `loadAgentRoster` has already resolved successfully — a failed load now leaves every piece of state exactly as it was, with only the error notice changing.
- **Security roles are business-unit-scoped, so one roleid was never enough — this is what "the dropdowns have 4 versions of each role" was.** Dataverse gives every business unit its own copy of each security role: same name, different `roleid`. A live environment's `role` table had four rows all named e.g. "Customer Service Agent" — one per business unit — which is exactly what showed up, unfiltered, in Round 10's per-group dropdown. Worse than the visual duplication: Round 10's `RoleSelection` stored a single specific `roleid` per group, so picking any one business unit's copy would have silently missed every candidate whose role assignment pointed at a *different* business unit's copy of the "same" role — a real coverage gap, not just clutter. The fix changes what `RoleSelection` stores: a role **name** per group (the business-unit-independent thing a person actually means by "the Agent role"), not a specific id. The picker's dropdowns now list each distinct name once; a new `resolveRoleIds` in `App.tsx` expands a picked name back to *every* roleid sharing it, across every business unit, right before the candidate query runs — so selecting "Customer Service Agent" once now correctly covers all four business units' copies of it, not just whichever one happened to be picked.

**Round 13 (2026-09-22) — two live-testing reports, both resolved without a code change plus one real fix.** The operator hit the exact Round 11 `teamrolescollection` error again after that fix had already merged, and separately reported the role picker's dropdowns still showing 4 copies of the same role name with nothing suggested by default. Direct comparison against source confirmed both symptoms belonged to code already fixed weeks-old at that point — a live check of the deployed `bundle.js`'s own content (`Contains 'teamrolescollection': True`) showed the *deployed* web resource was still the pre-Round-11 build; the Round 9-11 fixes had been merged to `main` but never actually redeployed to `academyexperiment` (`deploy.ps1 -Tool agentreadiness` last run before those rounds shipped). Redeploying fixed it. Then, retesting in an incognito window (to rule out this subarea's own "available offline" caching, which doesn't always clear on a plain hard refresh) confirmed dedup and default-suggestion were both genuinely already correct in the deployed build — closing those two out as pure staleness, not bugs.
- **The real fix**: the operator's own environment's actual relevant roles are "Omnichannel Agent"/"Omnichannel Supervisor"/"Omnichannel Administrator", but `suggestSelection` (App.tsx) picked the *alphabetically-first* role matching a loose keyword ("agent"/"supervisor"/"admin") — in an environment that also has generic "Customer Service ..." roles, those sort before "Omnichannel ..." alphabetically and won the guess, even though the Omnichannel-prefixed role is the one that actually governs contact-center/unified-routing access (a generic Customer Service role governs case/entity access, a different concept). Fixed by trying `DEFAULT_ROLE_GROUPS`'s named candidates first, in order (now "Omnichannel X" listed before "Customer Service X" in `config.ts`) — an exact case-insensitive name match beats an alphabetically-first substring match — falling back to the loose keyword substring only when none of the named candidates exist live (preserving Round 9's rename-survival behavior, e.g. "D365CC-Omnichannel-Supervisor").
- **Lesson**: a deploy-then-verify step needs to check the *live, deployed* artifact, not just that the fix exists in source/git — Round 11's fix was completely correct and had been sitting on `main` unreleased. Going forward, treat "operator still sees the old bug" as reason to diff the deployed bundle against source before re-diagnosing the code.

**Round 14 (2026-09-22) — Round 13's own fix still didn't work for the operator, plus a second, unrelated noise report.** After Round 13 deployed and was confirmed live (bundle content checked directly), the operator reported the correct Omnichannel roles still weren't pre-selected, and separately that the role dropdowns list "a lot of deprecated accounts", pointing at real live role names like `(Deprecated) Metadata Store Reader`.
- **Simulating `suggestSelection` directly against the real live role names first** (`Omnichannel Administrator`, `Omnichannel agent`, `Omnichannel supervisor` — confirmed via a read-only role-list query against academyexperiment, 940 role rows / 235 distinct names across 4 business units) showed Round 13's matching logic itself was correct — it does find these case-insensitively. The actual bug was one level up, in `connect()`: a saved selection from localStorage was applied **as a single all-or-nothing object** — `saved && savedStillValid ? saved : suggestSelection(roles)` — where `savedStillValid` only required *any one* previously-saved group to still name a real live role. A partial or stale selection saved during earlier testing (e.g. only "agent" ever picked, or picked before Round 13's fix existed) would satisfy that check and then get used wholesale, silently keeping the other two groups exactly as they were (possibly empty) instead of ever reaching the new, better suggestion. Fixed by reconciling per group in a new `reconcileSelection()`: each group independently uses its saved name if that name is still a real live role, otherwise falls back to that group's own suggestion — a stale/partial memory can no longer shadow a correct default for a *different* group.
- **The deprecated-roles complaint was real and separate**: Dataverse itself marks retired system roles this way (`(Deprecated) X`, and at least one `X(Deprecated)` suffix form, both confirmed in the live list), and none of academyexperiment's ~235 distinct role names are things this tool should ever suggest or let someone pick. `loadAllRoles()` (`dataverse.ts`) now filters out any name containing `(deprecated)` case-insensitively before it ever reaches the picker.
- **Lesson**: when a fix that's confirmed logically correct still doesn't manifest live, the next place to look isn't "is the logic wrong" (already ruled out by direct simulation against real data) but "is something upstream of the logic overriding it" — here, a persisted-state merge rule (all-or-nothing on saved data) that happened to matter only for operators who'd already interacted with an earlier, buggier version of the same feature.

**Round 15 (2026-09-22) — a design correction from direct operator feedback, not a live-testing bug report.** The operator flagged that `checkPresence` (`checks.ts`) was warning on an agent who was simply logged out at the moment the tool ran, having last been active less than a day earlier — their own read: a recent login is itself evidence the account/setup works, and only a genuinely stale-or-absent login should warn.
- **Agreed, and this is the same class of mistake Round 8 already named**: Round 5 correctly fixed a real bug (a stale "Available" presence label being read as current), but its fix — warn on `isLoggedIn === false` unconditionally — over-corrected. Most agents are logged out most of the time (off-shift, weekends), so that alone isn't a structural misconfiguration; "technically defensible" and "actually useful" diverged again, exactly as they did for Round 8's queue-membership-only roster inclusion.
- **The fix**: `checkPresence` now only warns on "not logged in" once the last known activity (`presence.capturedOn`) is older than `PRESENCE_STALE_THRESHOLD_DAYS` (`config.ts`, default 14) — recent-but-logged-out now passes, with evidence saying so explicitly. If `capturedOn` is missing/unparseable, it falls back to the original conservative warn (unchanged behavior for that edge case) rather than guessing an age. `checkPresence` gained an optional `now: Date` parameter (default `new Date()`) purely so this is testable without the test suite aging out.
- **A pre-existing demo fixture broke silently under the new logic**: `a-cynthia` ("messy multi-failure agent") had `presence.capturedOn` hardcoded one day before the file was last touched — under the new logic this flipped from warn to an unintended pass, quietly losing part of that fixture's story (though `demoData.test.ts`'s "presence reaches warn" coverage assertion still passed via two other agents, so nothing caught it automatically). Fixed by moving that date safely past the staleness threshold. Also added a new fixture (`a-chien`) whose `capturedOn` is computed relative to actual `Date.now()` at load time (not a fixed string) specifically so it demonstrates the new pass branch regardless of when the demo is viewed.
- **Lesson**: a fixed calendar date embedded in test/demo fixtures is a silent expiry timer on whatever behavior it's meant to demonstrate — any fixture whose purpose depends on "how long ago" should either sit safely past the threshold it's testing (if demonstrating staleness) or be computed relative to real time at load (if demonstrating recency), never a string that happened to be close to "today" on the day it was written.

**Round 16 (2026-09-22) — a feature request reviving, in a lighter-weight form, a concept this tool had already removed once.** The operator asked for the agent list sorted alphabetically with agents from a different email domain pushed to the end. Round 8 had a `homeDomain`/`loadCurrentUserDomain` concept for exactly this kind of domain awareness, but removed it entirely because it made a bad *filter* (a real agent can sit on a foreign domain and get wrongly hidden; a noise account can share the home domain and get wrongly kept) — that critique doesn't carry over to a *sort*, where the worst case of a wrong guess is just a few agents landing in the "wrong" half of an otherwise-alphabetical list, not silently disappearing from the roster.
- **Implementation**: `App.tsx` gained `majorityDomain()` — a self-contained heuristic (most common `@domain` among the currently loaded roster, no live query) rather than resurrecting a "who am I" lookup — used only to group the existing "Agent" name-sort column: same-domain-as-the-majority first (alphabetically), everyone else after (also alphabetically). Agents with no domain name at all stay in the primary group rather than being pushed down, since a missing domain isn't evidence of "another domain." The default `sortKey` also changed from `"status"` to `"name"` so this is what the list shows without an extra click, matching how the request was phrased ("have the user list sorted as follows").
- Verified visually in demo mode: with 25 `@contoso.com` agents and one `@fabrikam-systems.com` service account, the roster starts Ada/Adele/Alan/Annie/Barbara… and the fabrikam account is the very last row.

**Round 17 (2026-09-22) — live testing immediately after Round 16 shipped showed `majorityDomain()`'s heuristic itself was the weak link, exactly the risk Round 8 originally flagged about domain guessing, just showing up in a new spot.** The operator's own roster mixes real human agents with several application/service accounts (Copilot IVR bots, a routing app) that, in this Dataverse environment, share one auto-generated synthetic domain (a GUID-shaped `<environment-id>.com`, not a real organization domain). Counted by raw frequency, that shared synthetic domain could out-number the operator's own real, human-agent domain, so agents were still landing in the wrong half of the list — the operator's own account and a bot account ended up split across different sort groups with no obvious rule from the screenshot.
- **Fix**: added `loadCurrentUserDomain()` to `dataverse.ts` — a live, read-only lookup (`Xrm.Utility.getGlobalContext().userSettings.userId`, then a single `systemuser` retrieve for `domainname`) of the *connected user's own* domain, which `App.tsx`'s `homeDomain` now prefers over `majorityDomain()` whenever a live connection provides it; `majorityDomain()` is kept only as the fallback for demo mode or if the live lookup itself fails (best-effort — never throws, never blocks a connection). This is a live "who am I" lookup, the same shape of thing Round 8 removed for *filtering* — but the risk that removal was guarding against (a real agent wrongly hidden, a noise account wrongly kept) is specific to filtering; for sorting, using the operator's own domain as "home" is actually the more intuitive, stable reference than a frequency count that a handful of bot accounts can dominate.
- **Lesson**: this is Round 9/10's "a fixed list is a starting guess, asking the live environment is what's trustworthy" lesson recurring in a new shape — a *frequency-based* guess has the same fragility as a *fixed-list* guess whenever the population being counted isn't homogeneous (here: real agents vs. service accounts), and both are weaker than asking the one question that's actually unambiguous ("what's the connected user's own domain?") when that question is cheap and available.

**Round 18 (2026-09-22) — a design reconsideration prompted directly by the operator, not a bug report.** The operator pointed out that the "Agent information" panel's per-check list was showing the exact same evidence as the full "Outcome" checklist directly below it, just condensed — a straight duplicate rather than something that earned its own space. Asked for ideas rather than a fix, three directions were offered (remove the panel outright; trim to identity-only plus quick-action links; trim to identity plus an action-only summary) and the operator picked the action-summary option.
- **Implementation**: the panel keeps its identity header (avatar, name, domain, overall status pill — none of which appear in the checklist), but the per-check evidence list is replaced by a new "Needs attention" section: only checks with a status other than `pass` (fail/warn/unknown all carry a `suggestedFix` — see `model.ts`'s `CheckResult`), showing just the check's title and suggested fix, not its full evidence. An agent with nothing outstanding shows a plain "No action needed — every check passes" message instead of an empty list. `App.tsx` gained `attentionChecks` (a filter over the existing `checksByCategory`); `agent-info-value`/`agent-info-value-list` CSS (evidence rendering) was removed as dead code and replaced with `agent-info-title`/`agent-info-fix`/`agent-info-clear`.
- **Lesson**: not every "make this nicer" request is about visual polish — this one was actually about information architecture (two panels answering the same question in different-sized fonts isn't more useful than one), and the fix was to give the smaller panel a distinct *job* (triage: what do I still need to do) rather than trim or restyle its existing, redundant job.

**Lesson for future discovery on this tool**: (1) a plausible-sounding admin-UI concept name ("capacity profile") does not reliably predict the underlying entity shape — check directly, and when the *first* check comes up empty, that's a reason to search more broadly (by concept, not just the one name already guessed), not to conclude the concept doesn't exist. (2) Never copy a field name's casing from the maker portal's Columns UI into a Web API query — always lowercase simple/value fields. (3) A lookup's `$expand` navigation property name is a distinct piece of metadata from its lowercase `_value` alias and must be looked up (via `ManyToOneRelationships`), not assumed to follow either the logical-name or schema-name casing consistently — and this varies *per relationship*, not per table (compare Round 2's `Characteristic`/`RatingValue` PascalCase against Round 3/5's lowercase `msdyn_capacityprofileid`/`msdyn_currentpresenceid`, both confirmed by testing rather than assumed). (4) The single most reliable verification available was neither the maker portal UI nor guessing — it was the person testing their own live account and noticing the tool's answer didn't match reality, repeatedly (Rounds 3, 4, and 5). A live mismatch a real user reports is a stronger signal than any schema search on its own. (5) A field existing, being populated, and reading without error (`msdyn_capacityrequired = 30`; `systemuser.msdyn_defaultpresenceiduser` resolving without a 400) is not the same as that field meaning what its name suggests, or being the *only* field that could plausibly answer the question — a name that sounds right ("presence", "default presence") is a hypothesis to verify against live data, not a conclusion. (6) Not every check needs its own independent data source — sometimes the honest schema answer is "this concept doesn't exist separately, it's fully determined by data this tool already has," and asking the person who actually administers the environment settles that faster and more reliably than any further metadata search, especially when a candidate table exists but is empty and therefore unconfirmable either way. (7) The same underlying data can quietly mean two different things that a single field conflates — "we confirmed there's nothing here" and "we couldn't tell" are opposite conclusions, and collapsing them into one "undetermined" bucket (as both the skills and unified-routing-state fields did) hides a check that could already give a real answer behind one that never can; the fix in both Round 7 cases was to look again at data already being fetched, not to fetch something new. (8) A field's official description (available directly from `EntityDefinitions` metadata, as with `msdyn_isblockedbysomeprofile`) is worth reading in full before dismissing a broad keyword search as a dead end — the exact word imagined ("exclusion", "opt-out") not appearing anywhere doesn't mean the underlying concept has no real, live, first-party signal at all, just that the concept as imagined doesn't match how the product actually models it. (9) Not every live-testing correction is a wrong schema guess — Round 8 was a design choice (who counts as "in scope" at all) that was defensible on paper (surface every possible misconfiguration) but wrong in practice once a real, populated environment's noise floor was visible; "technically more thorough" and "actually useful" aren't the same goal, and a real user hitting the actually-noisy case is the only way to find that out. (10) A fixed list of "common" names for anything an org can rename or clone (security roles, in Round 9; the same risk applies to queues, teams, or business units) is a starting guess at best and a silent failure at worst — asking the live environment what it actually has, and asking the person to confirm which of those real things matter, survives renaming in a way no name list ever can. A loose substring/keyword match is what makes an automatic suggestion still useful after a rename (an exact-name guess is not), but the person confirming it is still what makes it trustworthy. (11) Dataverse security access is granted two ways — a direct role assignment and a role granted via Team membership — and they are equally real from the platform's own point of view; a tool that only reads `systemuserroles` is silently blind to an entire, common category of real users. Asking "could this also be true via a team?" *before* shipping a role-based feature (rather than waiting for a live gap report) would have caught this in the same pass as Round 9's main fix — worth defaulting to for any future check built around Dataverse's security model. (12) A functionally-correct fix can still be reported as "broken" if the interaction flow around it is confusing — Round 9's role resolution was right, but splitting "connect" into two required clicks (fetch roles, then separately confirm and load) with no strong visual signal that the first click had done anything made it look like regression rather than progress. When a feature is described as "worked before, doesn't now," check the flow the person actually experiences before re-auditing the data it's built on — the data was fine here; the sequence of clicks around it was the actual defect. (13) A fact confirmed via one calling convention (raw REST, needing an EntitySetName) does not automatically transfer to a different calling convention over the same data (`Xrm.WebApi`, needing a logical name) — when a live-discovery script and the tool's actual runtime code talk to Dataverse differently, a finding from the script needs translating, not copying verbatim, into the tool. (14) Updating one piece of derived state ahead of the asynchronous call it depends on succeeding is a real bug class, not a style nitpick — if a `setState` describes "what we're about to have," it belongs after the `await` that produces it, so a mid-flight failure can't leave two pieces of related state (here: which roles are active vs. which agents are loaded) each honestly reflecting a *different* moment in time. (15) Dataverse's own structural facts — like security roles being copied per business unit — are exactly the kind of thing a schema search (which checks *whether a table/column exists*) won't surface on its own, because the table and columns are completely ordinary; only looking at the actual *rows* returned (four "Customer Service Agent"s, not one) reveals it. When live data looks unexpectedly duplicated, the first hypothesis should be "this is really N distinct things," not "the query has a bug."

## Still open / not yet verified

- **The exact action/JSON shape a skill-identification step uses to set required skills**, when a step actually exists (see the README's confidence table) — the tool's honest limitation, not a bug; it degrades to "Not verifiable" for that specific queue rather than guessing. This is now the only field in this tool without full live confirmation.
- **Round 12 (2026-09-22) re-checked this rather than leaving it stale**: a read-only live query for `msdyn_routingconfigurationstep` rows with `msdyn_type eq 192350001` (Skill identification), with no workstream filter this time — i.e. the whole environment, not just the three inbound-voice workstreams Round 7 checked — returned zero rows. There is currently no Skill identification step configured anywhere in `academyexperiment`, so there's no live ruleset to read `extractRequiredSkills`'s guessed JSON shape against. A public-documentation search (Microsoft Learn) also came up empty — the admin-UI concept ("skill-based routing rules") is documented, but the underlying `msdyn_rulesetdefinition` representation it compiles down to is not. Closing this out for real needs either a step to exist live somewhere (a genuinely new one, or authored temporarily and removed afterward — the operator's call, since this tool never writes to Dataverse itself) or documentation that doesn't currently seem to exist publicly. Decided to leave it open rather than force either.
- **Very large rosters** — batched by-id reads (25 ids per OR-filter batch) and paging are implemented, but this hasn't been load-tested against a genuinely large (1000+ agent) environment, and the live role picker's own role list/table hasn't been tested against an environment with a very large number of security roles either.
- **Teams grant security roles (Round 9), but a team is still not itself an evaluated entity** — this tool evaluates individual `systemuser` agents only (including those who reach the roster via team-granted roles); team-based *queue* assignment or *capacity* is a distinct, still out-of-scope concept from team-granted roles.
- **Chat/other channel workstreams** — deliberately scoped to inbound voice, matching the toolbox's existing tools and the original "why isn't this agent receiving calls" (voice) ask.
